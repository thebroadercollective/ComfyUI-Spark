# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

ComfyUI-Spark is a fork of [ComfyUI](https://github.com/comfyanonymous/ComfyUI) (v0.27.0) optimized for the NVIDIA DGX Spark (GB10, sm_121, 128GB unified LPDDR5x memory). The core optimization goal is eliminating redundant memory copies during model loading — on unified memory, the standard ComfyUI loading pipeline creates 2-3x memory usage because it assumes separate RAM/VRAM pools.

## Common Commands

```bash
# Run ComfyUI (DGX Spark optimized flags). --disable-mmap is NOT used: GB10
# autodetection routes loads directly to CUDA, making it irrelevant/unnecessary.

# CUDA_CACHE_MAXSIZE=4GiB enlarges the JIT kernel cache to avoid recompiles.
CUDA_CACHE_MAXSIZE=4294967296 python main.py --listen 0.0.0.0 --port 8188 \
  --disable-dynamic-vram --reserve-vram 1 --disable-pinned-memory \
  --bf16-unet --bf16-vae --bf16-text-enc \
  --use-sage-attention --cpu-text-enc --verbose INFO --cache-aggressiveness high

# Lint (ruff is configured in pyproject.toml but is NOT a pinned dependency;
# `uv run ruff` fails after a dep resync — use uvx to fetch it ephemerally)
uvx ruff check .

# Install test dependencies (not in main deps)
uv pip install pytest pytest-aiohttp pytest-asyncio

# Run all tests
uv run python -m pytest

# Run unit tests only
uv run python -m pytest tests-unit/

# Run a single test file
uv run python -m pytest tests-unit/comfy_test/some_test.py

# Run tests by marker
uv run python -m pytest -m "not inference and not execution"

# Install dependencies

```

## Architecture

### Entry Point & Server
- `main.py` — Application entry point. Parses CLI args, initializes CUDA environment, loads nodes, starts server.
- `server.py` — aiohttp web server with WebSocket support for real-time progress updates.
- `execution.py` — Workflow execution engine. Walks the node graph, manages execution order, handles caching.

### Core Model Pipeline (`comfy/`)
The model loading and inference pipeline flows through these key files:

- **`comfy/cli_args.py`** — All CLI flags parsed here. Memory-relevant flags: `--disable-mmap` (do NOT add to the launch command: irrelevant on GB10 — autodetection already routes loads directly to CUDA), `--disable-pinned-memory`, `--disable-dynamic-vram`, `--reserve-vram`, `--bf16-unet/vae/text-enc`, `--cpu-text-enc`, `--highvram`, `--gpu-only`, `--lowvram`, `--novram`.
- **`comfy/cache_policy.py`** — Configurable cache-drop policy for model loading. `CachePhase` enum defines seven load-path phase hooks. `maybe_drop(phase)` checks the active preset/override/watermark and calls `soft_empty_cache_unified()` + optional `gc.collect()`. CLI flags: `--cache-aggressiveness {off,low,normal,high,paranoid}` (default: normal), `--cache-drop-at <phases>` (comma-separated override), `--cache-drop-threshold-gb <gb>` (pressure watermark). Call sites are in `sd.py`, `utils.py`, `model_management.py`. The module imports `model_management` at module level (safe: one-way dependency) and `cli_args.args`.
- **`comfy/model_management.py`** (~2150 lines) — Central memory management. Controls VRAM state (HIGH/NORMAL/LOW/NO/SHARED), model loading/unloading between CPU and GPU, memory estimation, and the soft/hard memory limits that trigger offloading. The `VRAMState` enum and `load_models_gpu()` function are critical. Contains memory observability helpers: `memory_report(*, device=None) -> str` returns `"alloc X.XG res X.XG free X.XG | sys avail X.XG used X.XG"` combining torch allocator + psutil views; `memory_delta(before, after) -> str` returns `"Δtorch +X.XG Δavail +X.XG"` from two snapshot strings; `soft_empty_cache_unified(force=False)` skips `ipc_collect()` on unified memory. Use these for any new load-path logging.
- **`comfy/model_patcher.py`** (~2200 lines) — `ModelPatcher` wraps loaded models, handles weight patching (LoRA, etc.), device movement, and memory tracking. `patch_model()` / `unpatch_model()` manage weight modifications.
- **`comfy/sd.py`** (~2200 lines) — High-level model loading. `load_diffusion_model()`, `load_clip()`, `load_vae()` orchestrate loading safetensors files into model architectures. Uses `comfy.utils.load_torch_file()` for the actual file I/O.
- **`comfy/utils.py`** (~1600 lines) — `load_torch_file()` is the universal file loading function. For safetensors, it uses `safetensors.safe_open()` with mmap. The `--disable-mmap` `tensor.to(device=device, copy=True)` copy path is guarded by `if DISABLE_MMAP and not unified:` (`comfy/utils.py:212`) — on unified memory the copy is skipped, which is why `--disable-mmap` is a no-op on GB10.
- **`comfy/ops.py`** (~1550 lines) — Custom PyTorch module wrappers (`Linear`, `Conv2d`, etc.) that handle dtype casting and device placement during inference.
- **`comfy/model_detection.py`** — Identifies model architecture from state dict key patterns.
- **`comfy/supported_models.py` / `supported_models_base.py`** — Model architecture definitions and configurations.

### Node System
- **`nodes.py`** (~2500 lines) — Built-in node definitions (CheckpointLoader, KSampler, VAEDecode, etc.). Node classes define `INPUT_TYPES`, `RETURN_TYPES`, and a main function.
- **`comfy_extras/`** — Additional node modules (samplers, controlnet, audio, flux, etc.). Each `nodes_*.py` registers node classes.
- **`comfy_api_nodes/`** — Cloud API partner nodes.
- **`custom_nodes/`** — User-installed custom node packages. Each subdirectory with `__init__.py` is auto-loaded at startup.

### Execution Pipeline (`comfy_execution/`)
- `graph.py` / `graph_utils.py` — DAG topological sort and execution ordering.
- `caching.py` / `cache_provider.py` — Node output caching strategies (classic, LRU, RAM-pressure, none).

### Key Data Flow: Model Loading
1. User triggers a loader node (e.g., `CheckpointLoaderSimple` in `nodes.py`)
2. Node calls `comfy.sd.load_diffusion_model()` or similar
3. Which calls `comfy.utils.load_torch_file()` to read the safetensors file
4. State dict is passed to model detection, then used to instantiate the model architecture
5. `ModelPatcher` wraps the model for memory management
6. `model_management.load_models_gpu()` handles device placement when inference begins

### Load-Path Observability
The load path emits INFO-level memory-accounting logs at phase boundaries. Key tags in chronological order: `LOAD` (file bookends + throttled progress ticks in `utils.py`; the bookend's `method=` field is one of `unified-cuda-stream` / `unified-cpu-stream` / `unified-cuda` / `cpu-explicit` / `cuda-explicit` / `aimdo` / `mmap` / `torch-pickle` and tells you exactly which load path ran), `CHECKPOINT` / `CHECKPOINT_SLICE` (entry/done bookends in `sd.py`), `DETECTED` (model config identification), `MODEL_INIT` / `UNET_LOADED` / `VAE_LOADED` / `CLIP_LOADED` (per-component snapshots), `LOAD_MODELS_GPU` / `POST_GC` / `LOAD_BUDGET` / `MODEL_GPU_READY` (inference-start sequence in `model_management.py`; `LOAD_BUDGET` reports model_size / loaded_now / free / min_required / resulting budget / fits_fully at the point `load_models_gpu` decides full-vs-partial load), `CACHE_DROP` (from `cache_policy.maybe_drop()`). Progress ticks are gated on file size ≥5GB AND INFO level. **Memory in these logs:** the system field is `sys free X avail Y used Z` (and load progress ticks show `free X avail Y`). `free` excludes buff/cache — it is the number that, when it nears 0, forces kernel page-cache reclaim / swap, so it's the one to watch during loads; `avail` includes reclaimable cache and masks that pressure. `memory_delta` reports `Δfree` alongside `Δtorch`/`Δavail` when both snapshots carry the free field. SageAttention logs `[attention] sageattn first call ok` on first successful call and an aggregate `[attention] shutdown` summary at process exit via `atexit`.

`PAGE_CACHE_DROP` lines appear after each file load when `--drop-page-cache` is passed or on unified memory (auto-enabled). Uses `os.posix_fadvise(fd, 0, 0, os.POSIX_FADV_DONTNEED)` — non-privileged, per-file, Linux-only. This drops the OS page cache for the loaded safetensors file, which on unified memory competes with model tensors for the same physical pool. The helper `drop_file_page_cache(filepath)` lives in `model_management.py`. This is distinct from `soft_empty_cache_unified()` which clears the PyTorch CUDA allocator cache — the two caches are independent: `torch.cuda.empty_cache()` does not touch OS page cache, and `posix_fadvise(DONTNEED)` does not touch the CUDA allocator.

`PAGE_CACHE_DROP_TICK` lines appear *during* tensor loading (at each progress tick, ~30s/5GB) for files ≥5GB, calling `posix_fadvise(DONTNEED)` mid-load to keep OS page cache in check. **Critical caveat:** on the `safe_open` load paths this mid-load drop is essentially a *no-op* — `safetensors.safe_open` holds the whole file mmap'd for the load's duration, and `fadvise(DONTNEED)` cannot evict pages that are mapped into a live page table (verified: 0 bytes evicted while an mmap is live, all evicted after munmap). The page cache there only drops at the post-load `PAGE_CACHE_DROP` (after the `with` block munmaps). The *effective* mid-load drop happens only on the **streaming loader** path (`method=unified-{cuda,cpu}-stream`, below), which reads via `preadv` (unmapped pages) so `fadvise` actually evicts. On a streamed load the TICK lines' `free` should stay roughly flat instead of falling ~the bytes copied.

**Streaming loader (`method=unified-{cuda,cpu}-stream`):** for unified-memory loads of files ≥5GB (gated additionally on: not `aimdo_enabled`, `preadv`+`posix_fadvise` available, and `safetensors.torch._TYPES` importable), `load_torch_file` uses `_stream_safetensors_to_device` (`comfy/utils.py`) instead of `safe_open`. It applies to **both** the unified-default CUDA target *and* an explicit-CPU target (the `--cpu-text-enc` / DualCLIPLoader `device="cpu"` path — e.g. the ~33GB mistral text encoder, which previously loaded via `cpu-explicit`/`safe_open` and leaked ~33GB of un-evictable page cache); the target device is `device.type` if explicit else `cuda`, and the `method=` tag reflects it (`unified-cuda-stream` / `unified-cpu-stream`). It parses the safetensors header itself, `preadv`s each tensor's bytes into a fresh buffer, reconstructs the tensor by handing those bytes to `safetensors.torch.load` on a one-tensor in-memory blob (so dtype/shape/packing coverage is **exactly** the library's — do NOT reintroduce a fork-local dtype map; the streamer reads `safetensors.torch._TYPES` for membership-only pre-flight validation), copies to the target device, and `fadvise(DONTNEED)`s every 512MB. Because the file is never mmap'd, the page-cache transient stays bounded (measured ~+0.5GB vs ~+6GB for `safe_open` on a 6.6GB cold subset; ~2.5× faster) instead of driving a transient 2× copy that fills swap. Any failure (unknown dtype, short read, parse error) logs a `WARNING` and falls back to `safe_open` via `_safe_open_load_safetensors` (the original path, extracted) — so a silent return to the slow path is impossible to miss. The original safe_open inline block now lives in `_safe_open_load_safetensors`; both the stream path and its fallback funnel through `load_torch_file`. Design + adversarial-review notes: `docs/superpowers/specs/2026-05-31-streaming-pread-loader-design.md`.

### DGX Spark Unified Memory Context
On the Spark, "CPU memory" and "GPU memory" are the same 128GB physical pool. The `--unified-memory` flag (auto-detected on GB10/sm_121) enables optimizations that eliminate two of three duplication layers:
1. **mmap page cache** — `safetensors.safe_open()` uses mmap internally (at the Rust level). Page cache pages persist even after tensor materialization.
2. **`copy=True` duplication** — ~~Eliminated~~. On unified memory, `load_torch_file()` loads directly to CUDA via `safe_open(device="cuda")`, skipping the copy. **Important**: The CUDA override only applies when no explicit `device` is passed to `load_torch_file()` (`device=None` → use unified default). Passing an explicit `device=torch.device("cpu")` bypasses the CUDA override — this is how `--cpu-text-enc` and the DualCLIPLoader `device="cpu"` option work, avoiding CUDA allocator OOM when loading large multi-component models (e.g., Flux2.dev).
3. **`load_state_dict(assign=False)` copy** — ~~Eliminated~~. `ModelPatcher.should_assign_weights()` returns `True` on unified memory, using `assign=True` to directly assign loaded tensors as model parameters.
4. **`assign=True` dtype normalization** — With `assign=False`, loaded tensor data is copied into pre-allocated parameter buffers, implicitly converting to the model's dtype. With `assign=True`, checkpoint dtypes are preserved as-is. Checkpoints with mixed dtypes (e.g., weights in bf16, biases in fp32) will produce mixed-dtype parameters. Models using `disable_weight_init` ops (like the VAE — hardcoded at `comfy/ldm/modules/diffusionmodules/model.py:10`) have no runtime dtype casting, so mixed dtypes cause `RuntimeError`. Fix: call `.to(target_dtype)` after `load_state_dict(assign=True)` to normalize. The diffusion model uses `manual_cast` ops (which do cast at runtime) ONLY when `pick_operations()` is given a non-None `compute_dtype` that differs from `weight_dtype`; when the checkpoint dtype is natively supported by the hardware (e.g. bf16 on GB10, where `unet_manual_cast()` returns `None`), `pick_operations` takes the `compute_dtype is None or weight_dtype == compute_dtype` branch and returns `disable_weight_init` instead (`comfy/ops.py:1550-1551`) — no runtime cast. So mixed-dtype diffusion checkpoints crashed too: Krea 2 turbo (`krea2_turbo_bf16.safetensors`) was the first hit, with 174 fp32 tensors (norms, modulation vectors, and edge linears including `first.weight`) mixed into an otherwise-bf16 checkpoint, producing a bf16-input-vs-fp32-weight `RuntimeError` on the first sampler step. Fixed: `load_model_weights` (`comfy/model_base.py`) now pre-casts mismatched tensors to the model's init dtype on the unified `assign=True` path before `load_state_dict` — see the new Development Rules bullet below.

See `dev-docs/dgx-spark-comfyui-loader-plan.md` for the original analysis and `docs/superpowers/specs/2026-04-05-unified-memory-loading-design.md` for the implemented design.

## Development Rules

- This Claude Code harness does NOT provide the `Grep`/`Glob` tools (calling `Grep` hard-fails with "No such tool available"). Search via `Bash` using `ugrep` (`ug`/`ugrep`) for content and `bfs` for file/path finding — both are installed for this purpose. The `Explore` agent also works for broad fan-out searches.
- Use `uv` for all Python environment management. The venv is at `.venv/` under the project root.
- `pip` is NOT installed in `.venv` — `python -m pip` finds nothing. Always use `uv pip …` / `uv sync` / `uv run`.
- `pyproject.toml` + `uv.lock` are the canonical dependency source (env is built by `uv sync`). `requirements.txt` is vestigial upstream baggage and does NOT match the installed env (e.g. it lists `comfyui-frontend-package==1.44.19` but `1.42.8` from pyproject is installed) — do not `uv pip install -r requirements.txt`. The two have drifted; this is intentional (documented, not reconciled). See `dev-docs/environment-setup.md`.
- Installing a custom node's `requirements.txt`: always add `-c constraints.txt` (repo root) so an unbounded dep can't break the fork. The Hunyuan node declares `transformers>=4.47.0` (no upper bound); `constraints.txt` pins `transformers==4.57.3`, `torch==2.12.0`, `numpy==2.4.6` to neutralize it.
- Linting uses `ruff` (config in `pyproject.toml`). Key ignores: E501 (line length), E722 (bare except), E402 (import order).
- Test framework is `pytest` with markers: `inference`, `execution`. Test requirements are in `tests-unit/requirements.txt`.
- Python target: >=3.10. Type annotations use 3.10+ syntax.
- `comfy/utils.py` cannot import `comfy.model_management` at module level (circular import). Use lazy import inside functions.
- `comfy/cache_policy.py` imports `comfy.model_management` and `comfy.cli_args` at module level. Call sites in `sd.py`, `utils.py`, `model_management.py` use lazy `import comfy.cache_policy as cache_policy` inside functions to avoid circular imports. Do not add a module-level import of `cache_policy` in these files.
- `comfy/cli_args.py` has `_VALID_CACHE_PHASES` (a frozenset of strings mirroring `CachePhase` enum values) used for argparse-time validation. A drift assertion in `cache_policy.py` confirms they stay in sync at import time.
- Weight assignment behavior is controlled by `ModelPatcher.should_assign_weights()` — do not check `UNIFIED_MEMORY` directly at load_state_dict call sites.
- On unified memory, `load_models_gpu()` **always full-loads** (`unified_full_load = bool(UNIFIED_MEMORY)` in the budget block → `lowvram_model_memory = 0` → uncapped). Rationale: the model is already physically resident in the pool by the time the budget is computed — `load_torch_file` loaded a CUDA-target model straight to CUDA (`alloc == model_size` on the `LOAD_BUDGET` line) — and this branch only runs for non-CPU targets anyway (CPU targets take `VRAMState.DISABLED` and skip it). The lowvram split saves nothing on unified memory (`offload_device == load_device`, so "offloaded" weights stay resident and just route through per-step cast-on-demand), and `loaded_size()` counts only the resident portion, so a capped budget drifts *down* run-over-run and flips ever more weights onto the cast path. A model too large for the pool would have OOM'd during the load (before this point), so there's no "doesn't fit" case left to degrade for — hence the unconditional full load rather than the earlier residency-probe (`_model_weights_on_device`, now removed) which produced a misleading `fits_fully=False` on the very first generation. Non-unified and `force_full_load`/`NO_VRAM` paths are unchanged. Watch for `LOAD_BUDGET ... fits_fully=True ... budget(usable) uncapped(full)` and a `loaded completely` (not `loaded partially`) line — including on the **first** generation.
- Pyright reports many pre-existing errors (missing imports for torch, numpy, etc.) due to venv resolution. These are not real issues.
- The `--unified-memory` flag is auto-detected on GB10 (sm_121) hardware via `is_unified_memory_system()` in `comfy/model_management.py`.
- Unified memory gotcha: `safe_open(device="cuda")` loads ALL tensors to CUDA, including non-weight metadata (e.g., tokenizer vocab). Any code calling `.numpy()` on such tensors must add `.cpu()` first — e.g., `tensor.cpu().numpy()`. On unified memory `.cpu()` is essentially free.
- `load_torch_file(device=None)` uses a sentinel pattern: `None` means "use default behavior (CUDA on unified memory)", an explicit device means "honor this device". Do not add boolean flags to override device — pass the device explicitly instead.
- The fork's `safe_open(device="cuda")` copy-elimination path is reachable ONLY while DynamicVRAM is disabled. Upstream's threaded DynamicVRAM/`aimdo` loader auto-enables on any NVIDIA non-WSL box — including GB10 — via `enables_dynamic_vram()` (`main.py`), and when active `load_torch_file()` takes a separate `aimdo` branch (`comfy/utils.py`) that BYPASSES the unified-CUDA path entirely. The documented launch command passes `--disable-dynamic-vram`, which is what keeps the fork's loader engaged. Dropping that flag silently routes loads through upstream's aimdo loader instead — so `--disable-dynamic-vram` is load-bearing for the memory optimizations, not just a tuning knob. A rebase that reworks `enables_dynamic_vram()`/`aimdo_enabled` gating can flip this default; re-verify the branch selection in `load_torch_file()` after any such rebase. **Upstream is actively deprecating this flag** — as of v0.26.0 (`833bfb57`) its startup warning now says the arg "will be removed soon" and pushes native fp8 formats instead; a new `--enable-dynamic-vram` flag also exists but defaults off, so the fork's `--disable-dynamic-vram` still wins (`main.py:239`). When a future sync removes the flag entirely, the fork's loader will need another way to force `enables_dynamic_vram()` False / bypass the aimdo branch in `load_torch_file()`. **Why aimdo is the wrong paradigm here (do not be tempted to adopt it on the Spark):** `comfy_aimdo` is a demand-paged VRAM virtual-memory system for *discrete* GPUs — it mmaps the model into read-only host RAM (`load_safetensors` in `utils.py`) and pages 32MB chunks into a bounded, watermarked `VRAMBuffer` on demand (`ModelVBAR.fault/unpin/set_watermark_limit` in `comfy_aimdo/model_vbar.py`, DMA'd via `host_buffer.read_file_to_device`). It has ZERO unified-memory awareness (no `unified`/`integrated`/`sm_121` checks anywhere in the package) and treats GB10 as an ordinary discrete GPU. On unified memory its premise is null (host RAM and VRAM are one 128GB pool, no scarce tier to page into) and its mechanism is harmful: it keeps the file mmap'd in host page cache AND copies pages into a separate VRAMBuffer — two copies of the same bytes in the same physical pool, exactly the 2x duplication the fork's direct `safe_open(device="cuda")` single-copy load eliminates. Disabling it costs nothing on Linux/unified (the only documented downside is unreliable VRAM estimates "especially on Windows"); `should_assign_weights()` still returns True via the `UNIFIED_MEMORY` branch with dynamic VRAM off. For a model larger than the 128GB pool, aimdo would page against the same exhausted pool and still not help — `--drop-page-cache` (auto-enabled) is the right lever, and beyond pool size you are simply OOM.
- The unified large-file load uses the **streaming loader** (`_stream_safetensors_to_device` in `comfy/utils.py`, `method=unified-{cuda,cpu}-stream`), not `safe_open` — see the "Streaming loader" paragraph under Load-Path Observability. Four invariants for anyone touching it: (1) **Dtype coverage is inherited from safetensors, never hardcoded.** The streamer validates header dtypes against `safetensors.torch._TYPES` (membership only) and delegates *all* reconstruction to `safetensors.torch.load` on a per-tensor in-memory blob. Do NOT key it on the fork-local `_TYPES` in `utils.py` (a strict subset missing e.g. `F8_E8M0`/`F4` — it would silently route newer quantized checkpoints to the slow fallback). (2) **It only engages with the `safe_open` fallback intact.** Gating: unified, not `aimdo_enabled`, size≥5GB, `preadv`/`posix_fadvise`/`_TYPES` available, and the resolved `stream_target` ∈ {cuda, cpu}; any error falls back to `_safe_open_load_safetensors` with a `WARNING`. A rebase reworking `load_torch_file`'s branch selection must preserve both the gate and the fallback (same rebase-risk locus as the aimdo branch above). (3) **It handles both CUDA and explicit-CPU targets.** Unlike the `safe_open(device="cuda")` copy-elimination path (which is CUDA-only and skipped for explicit devices), the streamer also covers the `--cpu-text-enc` / `device="cpu"` text-encoder load — `stream_target = device.type if explicit_device else "cuda"`, and `safetensors.torch.load(blob)[name].to(target_device)` honors it. This is what bounds the ~33GB mistral page-cache leak. The CUDA single-copy `assign=True` semantics still apply only to the CUDA target; the CPU target is a plain CPU load, same as `safe_open(device="cpu")` produced. (4) **`safe_open().keys()` yields sorted keys** — the streamer re-keys its returned dict in sorted order to be a byte-and-order exact drop-in; `tests-unit/comfy_test/test_streaming_loader.py` pins `list(keys)` equality (and byte-equality for both cuda and cpu targets), so don't "optimize" it back to header order. The `_safe_open_load_safetensors` fallback still runs the (now-known-ineffective) mid-load `PAGE_CACHE_DROP_TICK`; that's harmless but is NOT where the page-cache win comes from.
- The VRAM-mode flags (`--highvram`/`--gpu-only`/`--lowvram`/`--novram`) are inert or redundant on the Spark — do NOT add them to the launch command. They exist to tune the CPU↔GPU split, which unified memory collapses. (1) `is_unified_memory_system()` sets `UNIFIED_MEMORY=True` but does NOT change `vram_state` (SHARED is MPS-only, `model_management.py:581`); with no flag you run `NORMAL_VRAM`, the intended state. (2) `--highvram`/`--gpu-only` set `HIGH_VRAM`, whose main effect is making `unet_offload_device()` return the GPU device instead of `cpu` — but the fork already returns `get_torch_device()` unconditionally on unified memory (`model_management.py:1026-1032`, same for `vae_offload_device:1214-1218`), so `offload_device == load_device == CUDA` regardless. `--highvram` is thus a no-op for the diffusion model and VAE; `--gpu-only` additionally forces text enc / intermediates onto GPU, which fights `--cpu-text-enc`. (3) `--lowvram`'s only effect with dynamic VRAM off is routing text encoders to CPU (`cli_args.py:144`) — already done by `--cpu-text-enc` — plus enabling partial weight streaming (`lowvram_model_memory`, `:935-943`), which is pure churn within a single pool. (4) `--novram` is the same, harder. All of these also force `enables_dynamic_vram()` False (`cli_args.py:351`), but `--disable-dynamic-vram` already does that. The real pool levers are `--cache-aggressiveness` (torch allocator cache) and `--drop-page-cache` (OS page cache), not the vram modes.
- The RAM-pressure cache (`Use RAM pressure cache.` at startup, default cache type, `execution.py:117`) is the node-OUTPUT cache (intermediate latents/images/conditioning on the CPU device per `intermediate_device():1197`), NOT model weights. Its live half — `RAMPressureCache.ram_release(target)` (`comfy_execution/caching.py:527`) evicting cached outputs when `psutil` available drops below the headroom target — works regardless of dynamic VRAM and usefully bounds the output cache (defaults on 128GB: active ~10GB, inactive ~96GB, `main.py:289-290`; tune via `--cache-ram <active> <inactive>`). Its **pin-pressure** half is DEAD by design on the fork's path: the pin loop (`execution.py:784-792`) calls `free_pins()`, which only touches models where `is_dynamic()` is True (`model_management.py:656`); with `--disable-dynamic-vram` the base `ModelPatcher.is_dynamic()` returns False and `pinned_memory_size()`/`loaded_ram_size()`/`partially_unload_ram()` all return 0 (`model_patcher.py:1373-1382`), so `free_pins()` returns 0. Weight management on the Spark is handled by the single-copy load + `cache_policy`, not the aimdo pin system. **BUT the output-cache half CAN still free model weights, and did cause a bug:** the `CheckpointLoader` MODEL output *is* a cached node output — a `ModelPatcher` living in `RAMPressureCache.cache` — and `ram_release(target, free_active=True)` (`caching.py`) `del`s cache entries, dropping the patcher's last reference and freeing the resident model (tens of GB), forcing a multi-minute reload. The 60GB-aware `1e30` score in `scan_list_for_ram_usage` only tags *old*-generation patchers, so the *current* (active) model scored as a tiny default entry and got swept up. The trigger chain on the fork: `free_pins()` returns 0 → `freed < ram_shortfall` is always true → the handler escalates to `ram_release(free_active=True)` *every* node under apparent pressure; and `psutil.virtual_memory().available` underreports free memory on unified (freed weights linger in torch's CUDA reserved cache, counted as unavailable), so the shortfall never clears and the eviction loop runs past the CPU-tensor outputs into the resident model. Repro: load Flux2 (60GB) → gen → load Qwen (~47GB) → gen → switch back to Flux2 → gen; with Qwen still resident, `available` fell below the 10GB active headroom during the Flux2 load and the active model was evicted right after the sampler (before VAE decode; `alloc` already dropped to 2.8G at the VAE's `LOAD_MODELS_GPU` entry line). **Fix:** `ram_release` now skips current-generation entries holding a `ModelPatcher` on unified memory (`_outputs_contain_model_patcher`, `caching.py`), so the resident model survives while CPU-tensor outputs stay evictable (the real relief valve); stale old-gen models stay evictable too. Regression test: `tests-unit/comfy_test/test_ram_pressure_model_protection.py`. NOTE the related-but-distinct `free_memory` site (`model_management.py:~835`): through v0.22 upstream gated the "only free the shortfall" smart-memory logic behind `is_dynamic()`, so a non-dynamic model got `memory_to_free = 1e32` and was unconditionally "unloaded" by `load_models_gpu` (e.g. when the VAE loads). On unified this was *harmless* — `model_unload(1e32)` → `detach` → `unpatch_model(self.offload_device)` does `self.model.to(offload_device)` where `offload_device == load_device == cuda` (a no-op move), so the nn.Module weights stay physically resident and the cached patcher keeps them alive; the next `load_models_gpu` re-finds the patcher and reloads instantly. That is why every prior VAE decode was fine. As of the v0.24.0 sync upstream dropped that gate: non-dynamic models now also get shortfall-only `memory_to_free` when smart memory is on (`is_dynamic()` now only gates the `for_dynamic` sub-branch), so they may not be unloaded at all — strictly milder, same unified-memory conclusion. Only the `ram_release` `del` (which drops the patcher *object*) actually frees the weights. **KNOWN ISSUE — text-encoder thrash across batch-COUNT iterations under tight memory (to be addressed):** the `_outputs_contain_model_patcher` protection (`caching.py:564-566`) only skips eviction for *current*-generation entries (`used_generation[key] == self.generation`). On a batch-count run (the workflow re-executes N times, N separate `Prompt executed`), when iteration 2 starts `self.generation` increments but the text-encoder node hasn't re-run yet — so the previous iteration's TE patcher is now *old*-generation, falls outside the guard, and old-gen ModelPatchers are explicitly the **first** eviction target (`ram_usage = 1e30`, `caching.py:579-581`). Under tight free memory (`ram_release` fires) the CPU-resident TE is evicted and must be re-streamed next iteration. The expensive diffusion model survives this (it's held by a strong ref in `model_management.current_loaded_models`, independent of the node cache, so `del`-ing its cache entry frees nothing — whereas the TE cache entry IS its last reference, which is *why* the cache picks the TE). Verified on Flux.2 Dev (60G diffusion + 33G mistral TE, ~10G free): a 2-iteration batch-count run cost 57.8s then 109.8s — the +52s is entirely the 33G TE re-stream. Correctness is unaffected. **Mitigation (use until fixed): prefer batch SIZE over batch COUNT** — batch size = one execution, one generation, TE encoded once (batched conditioning), no eviction; batch count = N executions, TE thrashes. A real fix would protect the most-recent TE patcher across a generation boundary (or pin text encoders separately from the node-output cache).

- Unified memory gotcha: On Spark there are TWO independent memory caches that consume the shared pool. (1) **PyTorch CUDA allocator cache** (`torch.cuda.memory_reserved - memory_allocated`) — freed tensors that torch holds for reuse; cleared by `soft_empty_cache_unified()` / `torch.cuda.empty_cache()`. (2) **OS page cache** (`buff/cache` in `free -h`) — mmap'd file pages from `safetensors.safe_open()`; cleared by `posix_fadvise(POSIX_FADV_DONTNEED)` per-file or `echo 3 > /proc/sys/vm/drop_caches` (requires root). The gap between `torch free` and `sys avail` in `memory_report` output is primarily OS page cache. `--drop-page-cache` (auto-enabled on unified memory) addresses layer 2; `--cache-aggressiveness` addresses layer 1.
- Unified memory gotcha: `ModelPatcher.patch_weight_to_device` has two allocation hazards on unified memory. (1) The default `weight.to(offload_device)` backup is a full second allocation in the same pool — when `should_assign_weights()` is True and `inplace_update` is False, store the original `weight` in `self.backup` by reference. (2) The legacy patch pipeline builds `temp_weight = cast_to_device(..., copy=True)` as an fp32 full-model scratch and then `set_attr_param`s a fresh rounded tensor — that was another full-model allocation (the 2x floor that OOM'd Flux2+LoRA). Fix: on the `should_assign_weights()` path, if all patches for the key are purely additive constant deltas (plain LoRA/LoHa/LoKr/GLoRA without DoRA, or raw `diff` patches — see `_patches_are_invertible` in `comfy/model_patcher.py`), compute `delta = calculate_weight(patches, torch.zeros_like(weight, dtype=fp32), key)`, stochastic-round to the weight dtype, and `weight.add_(delta)` in place. Store an invertible marker (`WeightBackup(weight=None, invertible=True)`) in `self.backup`; `unpatch_model` re-derives the delta from `self.patches[key]` and calls `weight.sub_(delta)` via `_invert_fast_path_weight`. Non-invertible patches (`set`, `model_as_lora`, DoRA/OFT/BOFT/bypass, non-None `function`, `offset`, `strength_model != 1.0`, shape mismatches) fall back to the legacy copy path for correctness. **fp8-scaled checkpoints also never take the fast path:** the gate is `convert_func is None` (`comfy/model_patcher.py:935`), and fp8-scaled ops carry a `convert_<weight>` dequant function (`get_key_weight`, `:247`) — you can't `add_` a delta into fp8-packed bytes in place, so the legacy path dequantizes (`temp_weight = convert_func(temp_weight, inplace=True)`, `:976-977`) and stores a backup. Observed cost on Wan 2.2 (two fp8 14B experts, lightx2v 4-step LoRA): patching bumped `alloc` ~+13G **per expert** (dequant + patched-weight materialization + backup) — harmless on the 128GB pool (bottomed ~47G free) but it is NOT the near-zero in-place cost the fast path gives bf16/fp16 models. This is by-design correctness, not a regression; the invertible optimization only ever applied to non-fp8 weights (the Flux2 bf16 case it was measured on). Watch this line if many LoRAs are stacked on both fp8 experts at once. Any new code path that reads `bk.weight` from `self.backup` must first check `bk.invertible` (always present on `WeightBackup`) and use `_invert_fast_path_weight` / `_compute_rounded_delta` or skip as appropriate. Critical asymmetry: `ModelPatcher.clone()` shares `self.backup` *by reference* across clones (via `get_clone_model_override`) but *copies* `self.patches`. An invertible `WeightBackup` written by a LoRA clone will later be observed by the base patcher during `unpatch_model`, where `self.patches[key]` no longer exists — so the patch list needed to recompute the delta must be stored *inside* the `WeightBackup` itself (`bk.patches`), not read from `self.patches`. All invertible callsites (`_invert_fast_path_weight`, `_compute_invertible_unpatched`, `_compute_rounded_delta`) take an explicit `patches` argument threaded from `bk.patches` for this reason. The dynamic loader's `ModelPatcherDynamic.restore_loaded_backups()` (called by both `load()` and `partially_unload()`) is also an invertible-aware restore site — it branches on `bk.invertible` and calls `_invert_fast_path_weight(key, bk.patches)` rather than `set_attr_param(self.model, key, bk.weight)`. Upstream owns that helper, so a rebase that refactors it will drop the branch and re-introduce the plain `set_attr_param` (which writes `weight=None` into the parameter); re-establish the branch inside the helper — this was the 2026-05-25 rebase conflict.
